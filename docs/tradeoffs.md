# 数据流追踪的两处取舍

本文记录 `stock_dashboard.py` 缓存与执行模型中两个有意为之的取舍，
配合 `trace/graph.json` 与浏览器追踪页（`python trace/server.py`）一起看。

## 1. 缓存键：只挂 ticker，还是叠加周期与参数

数据获取层刻意拆成两个 `st.cache_data` 函数，而不是一个键吃所有情况：

- `fetch_price_history(symbol, period)` — 键为 **ticker + 周期**
  （`fetch_price_history:{symbol}:{period}`，TTL 900 秒）。K 线历史对
  `period`（`1mo/3mo/6mo/1y/2y/5y`）敏感：同一只票切换周期，返回行数、
  指标窗口都不同，必须把 `period` 纳入键，否则切到 `5y` 会错误命中 `1y`
  的旧帧。追踪页左侧输入 ticker 后，右侧缓存键列会实时预览
  `fetch_price_history:AAPL:1y`。
- `fetch_stock_info(symbol)` — 键为 **只挂 ticker**
  （`fetch_stock_info:{symbol}`，TTL 900 秒）。公司名、行业、市值这类元数据
  与分析周期无关，也没有其它影响结果的入参；再叠加 `period` 只会制造永远不
  共享的冗余副本，切周期时平白多打一次网络请求。

**为什么不把全部入参都序列化进键。** 下游计算函数（技术指标、ML 特征）接收的
是整段 DataFrame；若把 DataFrame 内容也哈希进键，每次取数都会换键、缓存形同
虚设。因此缓存边界画在“会产生网络往返”的取数层，键只由**真正决定远端响应的
标量参数**（ticker，必要时加 period）构成；DataFrame 只作为缓存命中后的返回值
在函数间传递。代价是：当某个被忽略的隐含维度（如拆复权口径、数据源分页策略）
变化时，900 秒 TTL 之内会读到旧数据——这就是页面上“刷新”按钮调用
`fetch_price_history.clear()` 与 `fetch_stock_info.clear()` 精确清除对应条目、
而非依赖 TTL 的原因（见 `trace/graph.json` 的 `invalidations`）。

**与 `st.session_state` 的分工。** 缓存键是跨会话、按参数共享的（不同用户看同一
只票同周期可命中同一条），而 `session_state`（`last_symbol`、`refresh_count`、
`analysis_history`）是每个浏览器会话私有的 UI 状态，不进缓存键。追踪页中缓存键
用橙色、session_state 键用紫色区分，避免把“跨用户复用”和“本次会话记忆”混为一谈。

## 2. 整体重跑与阻塞式调用如何并存

Streamlit 的执行模型是**整体重跑（top-to-bottom rerun）**：任何控件变化都会从
`main()` 顶部重新执行整个脚本。而 `yfinance` 取数、RandomForest 训练都是
**阻塞式同步调用**，脚本必须原地等待返回。两者并存靠三层手段：

1. **用缓存把阻塞调用移出“每次重跑”的关键路径。**
   取数被包进 `@st.cache_data`。第一次（或 TTL 到期 / 手动清除后）重跑会真实
   阻塞一次并把结果写入缓存；之后切 checkbox、切标签页这类重跑命中缓存，阻塞式
   网络调用被一次内存读取替代。追踪页边的“复用/重算”颜色即表达这条边界：
   绿色=同一标签页内可复用，橙色=标签页外、每次执行都重新计算。
2. **用 `st.spinner` 承接无法避免的阻塞。**
   取数、指标计算、模型训练处保留同步调用，但各自包在 `st.spinner` 上下文里；
   因为它们是纯同步阻塞，不引入线程/队列，也就没有跨线程读写
   `session_state` 的竞态。整体重跑期间旧脚本实例被 Streamlit 作废，阻塞结果
   只会回到最新一次运行。
3. **手动失效与整体重跑解耦数据新旧与 UI 状态。**
   “刷新”按钮先对两个缓存函数执行 `.clear()`（精确丢弃 ticker/period 条目），
   再递增 `session_state["refresh_count"]` 并 `st.rerun()` 触发一次干净的整体
   重跑。缓存失效（数据维度）与脚本重跑（执行维度）是两个动作，组合起来才得到
   “强制重新取数”的语义；单纯 `st.rerun()` 不清缓存只会重新命中旧数据，单纯
   `.clear()` 不重跑则当前页面仍展示旧帧。

**代价。** 阻塞调用期间整个脚本运行是串行等待的，无法并发分析多只股票；这是为
了换取模型可被静态追踪——调用链全部是普通的同步函数调用，AST 能逐边落到源码行。
一旦引入 `asyncio`/线程池或回调，这些边就会落入追踪页的「不可解析」类别；当不可
解析占比超过 15% 时页面整体转灰且不给结论，正是为了防止在数据流不可信时输出误导
性的“已复用/已重算”判断。
